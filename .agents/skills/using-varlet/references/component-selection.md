# Varlet 组件选型与精简判断

## 决策顺序

1. **直接使用 Varlet**：现有组件的 props、slots、events 和默认主题可以满足需求。
2. **组合或轻量适配 Varlet**：只缺少布局编排、少量状态协调或 Vela token 映射。
3. **下沉 Vela Admin**：能力属于通用后台场景，且会被多个页面、生成项目或外部用户复用。
4. **保留 example**：内容依赖 mock 业务、品牌、权限数据或只服务单个演示页面。
5. **手写 UI**：仅在前四项都无法覆盖时考虑。

## 视觉等价门槛

替换前逐项确认：

- 默认 padding、gap、字号、行高、圆角、边框和背景是否一致。
- hover、focus、active、disabled、loading 和 ripple 是否改变。
- 浅色、深色、MD2、MD3 下是否仍使用正确 token。
- 375、768、1024、1440 视口的换行、滚动和信息密度是否一致。
- 标签、ARIA、键盘操作和 focus 可见性是否退化。
- 测试选择器、动态 class、脚本查询和 `:deep()` 是否依赖旧 DOM。

任一项无法证明等价时，先保留现状或只删除独立冗余，不做组件替换。

## Framework 下沉条件

满足以下任一项才进入 framework 评估：

- 同一交互或结构已在两个以上页面重复。
- 生成项目普遍需要该后台能力。
- 能力需要稳定 API、测试、主题或可访问性约束。
- 逻辑与具体业务数据、品牌或 mock 身份无关。

以下内容默认留在 example：品牌 Logo、GitHub 链接、mock 通知、mock 用户菜单、演示文案和一次性业务卡片。

## 参数与设置精简

- 按 layout、theme、tabs 等内聚领域组织对象，避免大量平铺 primitive 参数。
- 已发布 props、events 或配置字段必须先保持兼容并登记弃用。
- 新旧接口同时存在时必须定义优先级并增加兼容测试。
- 不使用全能壳组件隐藏复杂度；受控组件仍应允许业务替换各领域状态。

## 常见误判

- `var-card`、`var-cell` 等组件自带结构和默认样式，不是所有 `div` 都适合替换。
- class 出现在模板中不代表冗余；它可能承载 scoped 样式、响应式规则或测试选择器。
- Varlet 有同名组件不等于行为等价，必须核对当前版本源码和文档。
- 只减少调用方参数但把同样数量藏进不透明对象，不算真正精简。
