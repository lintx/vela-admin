# 使用中央注册表管理公开 API 弃用生命周期

## 状态

已采纳。

## 日期

2026-07-30。

## 背景

公开 API 的弃用信息此前只存在于源码注释和个别 ADR 中。随着兼容项增加，维护者难以稳定回答哪些属性仍需保留、何时可以评估删除，以及源码、迁移说明和发布版本是否一致。

治理需要同时满足两个约束：严格拦截漏登记或文档漂移，但不为每次开发增加 Git hook、启动扫描、后台轮询或自动删除行为。

## 决策

1. 根级 `deprecations.json` 是弃用生命周期的机器可读权威来源。
2. 每项使用稳定 `VA-DEP-NNN` ID；active 项的源码 `@deprecated` 注释必须携带该 ID。
3. 注册表保留 active 和 removed 历史，记录弃用版本、替代方案、迁移方式、最早移除版本、条件和实际移除版本。
4. `scripts/deprecations.js check` 双向校验注册表与源码，并检查生成的 `docs/deprecations.md`。
5. `scripts/deprecations.js audit` 只根据当前包版本报告达到最早移除版本的 active 项，退出成功且不修改文件。
6. AI 仅在准备执行 sandbox checkpoint 或用户明确授权的 commit 前，每个批次运行一次 audit；不使用 hook、任务启动检查、状态文件或周期任务。

## 影响

正面影响：弃用项可查询、可测试、可生成用户文档，长期任务不会依赖个人记忆；发布检查能阻止源码注释或文档与注册表漂移。

成本与风险：新增公开弃用项时必须同时维护注册表与源码 ID；最早版本只是候选门槛，仍需人工判断迁移窗口、安全风险和 breaking change 计划。

## 替代方案

### 只维护源码注释

无法表达包版本、移除条件和历史状态，也难以生成统一文档，因此不采用。

### Git hook 或每次任务启动自动检查

能更早提示，但会增加普通开发成本、环境耦合和重复 token 消耗；本项目只要求 AI 在 checkpoint/commit 前执行一次轻量 audit。

### 达到版本后自动删除或阻断测试

版本门槛不能证明生态调用方已迁移，也不能替代 breaking change 审核，因此 audit 只报告候选，不自动修改或失败。
